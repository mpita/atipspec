# Artifacts

Specifications and plans use Markdown with small YAML frontmatter. Evidence,
approval records and report receipts use JSON; signatures are detached SSH files. The CLI parses a
few line shapes and ignores HTML comments and fenced code, so the templates
can carry guidance the model deletes as it writes.

## Identifiers

| Kind | Format | Scope |
| --- | --- | --- |
| Delivery, capability, initiative, decision slug | `[a-z0-9-]`, e.g. `password-reset` | project |
| Requirement | `REQ-001` | capability, stable across deliveries |
| Acceptance criterion | `AC-001` | capability, stable across deliveries |
| Task | `T1` | the delivery |
| Finding | `F1` | the review |
| Decision | `DEC-001` | project, never reused |

## `spec.md`

```markdown
---
title: "Password reset"
status: draft          # draft or ready; `atipspec accept <slug> spec`, run by a person, sets ready
kind: feature          # or fix: a defect repair, one regression criterion, no plan acceptance
capability: auth       # living spec that receives the requirements on deliver
impact: [notifications]  # other living specs or contract sections touched
owner: ana
ticket: SHOP-12
initiative: null
base: 9f2c1e...        # commit the delivery started from; diff and rules use it
created: 2026-09-12T15:41:45Z   # `status` shows the age from here
---

# Password reset

## Intent

## Requirements

### REQ-001: Behavior title
Description.

Why: the reason, one line.

Acceptance criteria:
- AC-001: When <trigger>, the system <observable outcome with concrete values>.
- AC-002 [manual]: When <trigger>, a person observes <outcome>.

### REQ-002 [remove]: Behavior being removed
- AC-003: If the removed behavior is requested, then the system responds with <outcome>.

## Quality attributes

## Assumptions
- None

## Out of scope

## Open questions
- None
```

Parsed: `### REQ-nnn[ [remove]]: title` headings (levels 2 to 4),
`- AC-nnn[ [test|manual]]: text` lines under a requirement (`[manual]` marks
a criterion a person observes; the plan must list it under `Manual:`), list
items under `## Assumptions` and `## Open questions` (`- None` counts as
empty). `Why:` lines and examples are for people and the reviewer. See
[writing criteria](spec-quality.md) for the form `check` expects.

## `plan.md`

```markdown
---
scope: ["shop/auth/**", "tests/auth/**"]
---

# Plan: Password reset

## Approach

## Tasks

### T1: Task title
Covers: REQ-001, REQ-002
Tests: AC-001, AC-002
Verify:
- `python -m pytest -q tests/auth`
- `ruff check .`

### T2: Observed only
Covers: REQ-003
Manual: AC-003
Verify: none
```

Parsed: `### Tn: title`, a `Covers:` line with REQ ids, a `Verify:` line
followed by list items (backticks optional) or the word `none`, an optional
`Report:` line with the JUnit XML the commands write, and an optional
`Proof:` line followed by `- AC-nnn: test id` items that `check` verifies
against the evidence (see [build](../flow/build.md)). `scope` in
the frontmatter lists globs of the files the tasks may change, with the
[glob syntax of the contract rules](contract-rules.md#globs): `check` warns
about touched files outside them, deletions included (an error with
`strict_scope: true`), and the review packet lists them. Files under
`.atipspec/` never count. An empty or missing `scope` declares nothing.

## `review.md`

Written only by the reviewer.

```markdown
---
tree: <fingerprint from the packet>
reviewer: <client or model>
---

## Criteria
- AC-001: PASS. proof pointer
- AC-002: FAIL. precise gap

## Findings
- F1 [blocker]: text
- F2 [major]: text
- F3 [minor]: text

## Notes
```

Every criterion needs exactly one verdict with a proof pointer or failure
reason. Blocker and major findings block; deferring either needs a trusted risk
approval with expiry. Minor findings inform.

## `deferred.md`

```markdown
- F2: reason, and where it will be handled
```

Only findings can be deferred. An `AC-` or `REQ-` entry is an error.

## `brief.md`

The explore phase's output: Problem, Today, Options, Recommendation,
Questions for the user. Not parsed; included in the context.

## `evidence/Tn-<timestamp>.json`

Generated by `atipspec verify`: schema version, delivery, task, result, tree
before/after, head, timestamps, environment and exact commands with exit codes,
duration, output tail, full log path and log hash; with a `Report:`, the copied
JUnit XML with its hash and every test case with its status. The latest file per task
counts. Trusted CI attestation adds signer, repository, policy digest, run URL
and a detached `.json.sig` signature. Unsigned files are local evidence only.

## `specs/<capability>.md`

The living spec retains `### REQ-nnn: Title` sections and `AC-nnn` criteria.
`deliver` updates by stable ID, preserving identity on rename. Every living
requirement and acceptance criterion must have an ID from the start.

## `decisions/DEC-nnn-<slug>.md`

```markdown
---
id: DEC-003
title: "Use httpx for outbound HTTP"
status: accepted        # proposed, accepted, superseded, rejected
affects: [contract:dependencies, notifications]
supersedes: null
date: 2026-09-12
---

## Context
## Decision
## Alternatives
## Consequences
## Revisit when
```

`context` loads accepted decisions whose `affects` names the delivery's
capability, an impact entry, `contract` or `*`.

## `initiatives/<slug>/roadmap.md`

```markdown
## Deliveries
- orders-api: Orders API
- orders-screen: Orders screen

## Interfaces
```

Parsed: `- <slug>: title` lines under `## Deliveries`. Status per delivery
is derived: pending, its current status, or delivered.

## Derived status of a delivery

| Status | Meaning |
| --- | --- |
| `draft` | spec not accepted for its current content |
| `ready` | spec accepted, no plan yet |
| `planned` | plan with tasks, nothing committed; with `approve_plan`, the plan needs acceptance too |
| `in_progress` | some tasks committed |
| `implemented` | all tasks committed, gate not green |
| `checked` | local checks green; no authenticated acceptance |
| `verified` | trusted gate green with approved policy, signed CI evidence and human approvals |
| `delivered` | merged into the living spec and archived |

## Approvals and receipts

`approvals/local-spec.json` and `approvals/local-plan.json` are written by
`atipspec accept`: kind `local-acceptance`, phase, subject hash, who and when.
They are drift detection for the local gate and are ignored under a policy.

Signed `approvals/*.json` records phase, identity, role, approved timestamp,
subject hash, repository, policy digest and optional expiry. Each has a `.json.sig`
SSH signature. Provider records also carry PR/MR identity and source URL, and
are revalidated against the provider at acceptance time. `reports/acceptance.json`
is the archived receipt and artifact index. See [enterprise acceptance](../enterprise.md).
